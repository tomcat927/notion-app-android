## 一、先破一个前提：App 里没有代码块渲染逻辑

在 `notion-app-android` 全库搜索以下关键词，**零命中**：

```
code_block / codeblock / 代码块 / prism / highlight / shiki / monaco / codemirror
```

结论：代码块的排版、语法高亮、字体，**全部由 Notion 官方前端（SPA）完成**。
App 只是 WebView 容器。「代码块加载慢」不是 App 渲染代码的问题。

## 三、真正的根因：一次 3 秒内的网络集体超时

### 决定性证据

统计全部 8 份日志的 `syncRecordValue` 超时次数：

| 日志文件 | 超时次数 |
|---|---|
| diagnostic-20261009-154820.txt | 0 |
| diagnostic-20261009-155143.txt | 0 |
| diagnostic-20261009-161842.txt | 0 |
| diagnostic-20261009-165033.txt | 0 |
| diagnostic-20261009-171639.txt | **244** |
| diagnostic-20261009-172538.txt | **244** |
| diagnostic-20261008-*.txt | 0 |

**244 次超时全部集中在 17:13:53.930 → 17:13:56.654 —— 不到 3 秒内爆发。**

同一窗口内（17:13:53~17:13:57）共 315 条 js error，构成：

| 错误类型 | 次数 | 归属 |
|---|---|---|
| `syncRecordValue: Timed out` | 244 | Notion API（app.notion.com） |
| CORS blocked | 36 + 8 | 第三方资源 |
| `Failed to connect to splunk` | 10 + 7 | splunkcloud（已被 App 拦截，此为旧版残留） |
| Statsig 网络错误 | 4 + 3 | exp.notion.com |

**多域名同时失败 = 整条网络链路瞬间断了，不是某个接口慢。**

### 时间线还原

```
17:13:10  打开「刷机全攻略」
17:13:15  target page committed（首屏骨架已渲染）
17:13:22  采样1：269 资源 / 22,959ms   ← 正常
17:13:53  ⚡ 网络集体超时开始（3 秒内 244 次 syncRecordValue 超时）
17:13:56  ⚡ 超时结束
17:14:21  采样2：974 资源 / 1,069,716ms ← 累计耗时爆炸
```

也就是说：**代码块（以及图片、附件）不是"慢慢加载"，而是在 17:13:53 那一刻，它们的数据请求全部一次性失败/超时了。**

---

## 四、为什么会集体超时？两条链路归属

`syncRecordValue` 是 Notion 拉取**单个 block 内容**的接口，代码块/图片/附件都靠它补数据。
该请求走 `app.notion.com`，而 App 的 WebView 经系统代理（Clash）转发 —— 见
`MainActivity.applyWebViewProxy()`。

所以超时的直接原因是：**17:13:53 前后，Clash 代理链路对 `app.notion.com` 出现了瞬时故障/断流**，
导致同一批并发请求集体超时。代码块只是"受害者之一"，且因为它依赖逐 block 拉取，
在视觉上会比纯文本 block 更明显地表现为"长时间空白"。

### 旁证

- 同一批日志里还有 `https%3A%2F%2Fs3-us-west-2.amazonaws.com%2Fsecure.notion-sta...`
  的请求，耗时 **52,784ms、0 字节** —— 同样是代理链路上的长时间挂起。
- 无超时的 4 份日志（154820~165033）说明**代理正常时，代码块加载完全没问题**。

## 五、结论

1. **代码块本身不慢，也不特殊。** 用真实 block 数据验证：含代码块笔记的平均资源量（550）
   与无代码块笔记（562）**几乎相同**；完整采样下同为 972~986 资源 / 14.5~15.3MB。
   → 代码块**没有**带来任何额外资源加载。

2. **含代码块是常态（60%）**，日志打开过的 15 篇可读笔记里 9 篇含代码块。
   所以「代码块加载慢」和「笔记加载慢」在统计上几乎是同一件事，无法用"是否含代码块"区分。

3. **"慢"的观感来自代理链路的瞬时断流。** 244 次 `syncRecordValue` 超时在 **3 秒内爆发**
   （17:13:53.930 → 17:13:56.654），是多域名同时失败的链路级故障特征，而非单点资源慢。
   决定性反证：**同一次打开的不同采样，含代码块的笔记 totalMs 能差 46 倍**（22,959 → 1,069,716），
   而 code=0 的笔记反而稳定在 2 倍内 —— 若是代码块导致慢，不该有这种自相矛盾的波动。

4. **决定 totalMs 的是网络状况，不是 block 类型。** code=0 的笔记也能出现 273,751ms 的采样，
   与含 code 的 234,107ms 同级。

5. **日志层无法区分代码块**（SPA 不打印相关 DOM/字体/资源语义，JS 全是 webpack 哈希名），
   所以这个问题的可观测性天花板在「网络层」，不在「渲染层」。

6. **可优化点明确**：
   - 给 `app.notion.com` 的 API 单独指定更稳的节点或直连（避免与图片 CDN 抢带宽）；
   - 复核 WebView 代理透传策略（不翻墙时应尽早 `clearProxyOverride`）；
   - 增加 `syncRecordValue` 超时的重试/降噪探针，便于下次定位。

## 六、验证方法（可复现）

真实 block 数据通过 `notion-mcp-setup` 的凭据直读 Notion API 获得，脚本在 workspace 根：

```python
# verify_blocks_all.py —— 统计指定页面真实 code block 数
GET /v1/blocks/{page_id}/children?page_size=100   # 递归（toggle/column 下钻）
统计 type == "code" 的块数
```

- `verify_blocks.py` —— 初版，指定页面清单
- `verify_blocks_all.py` —— 扩展到日志中全部页面
- `cross_check.py` —— 交叉：日志打开过的页面 × 真实 code 数
- `correlate.py` —— 把 code 数对齐到 perf 采样并分组统计

**限制**：3 个页面（京东云路由器刷机 / 测试777 / 远程日志专用openlist账号密码）返回
`HTTP 404 object_not_found` —— 集成未被授权读取其 blocks（非页面不存在）。
这 3 篇在报告中标记为"无法验证"，未纳入分组统计。
